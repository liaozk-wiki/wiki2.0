# 概述

数据密集型系统设计，表明了针对的是数据密集型而非计算密集型，关注的核心是数据，而非计算。以数据作为核心视角如何来认识应用软件系统？

一般意义上的软件系统结构：

1. 客户端
2. nginx+网关
3. 无状态的业务服务层，相互之间rpc远程调用
4. 服务治理：注册中心、配置中心
5. 服务监测：日志服务、链路追踪、预警告警
6. 外围辅助中间件：MQ、缓存
7. 底层的存储状态的数据库



从数据视角则是：

1. 数据库
2. 缓存
3. 索引
4. 批处理
5. 流处理



这本书从整体上的内容大致是：

- 基础单机：如何从现实世界抽象出数据，到数据如何在一台机器上存储与索引，再到数据如何在多台机器之间进行传输。
- 分布式集群：此时数据已经多到一台机器无论如何都放不下的地步，需要多台机器共同构建一个逻辑上的完整数据库，涉及到数据如何复制、如何分区、为了简化编程模型，提供事务，但数据跨多台机器，如何处理一致性与共识以达到逻辑上的一个整体？
- 跨系统多集群：业务进一步复杂，需要多种不同类型数据存储统一提供服务，开始涉及批处理、流处理，最后就是究极四海归一：不同类型的数据存储集群，如何统一起来，作为一个抽象的数据存储层统一对外服务？



让我们一起来抽丝剥茧！

# 如何描述数据系统？

一个最高层级的指标：可靠性、可拓展性、可维护性

| 维度         | 核心问题           | 关键手段                                  | 洞察                                           |
| ------------ | ------------------ | ----------------------------------------- | ---------------------------------------------- |
| **可靠性**   | 故障下系统依然可用 | RAID/灾备（硬件）、测试/隔离/兜底（软件） | "可以慢，但绝不错"——金融系统的唯一准则         |
| **可拓展性** | 负载增长时如何应对 | 垂直拓展优先、水平拓展兜底；p50/p95/p99   | "几个强大的服务器，仍然比大量虚机更简单更便宜" |
| **可维护性** | 系统能否活得久     | 简单性（抽象）、可演化性                  | 运维成本 >> 开发成本                           |



# 如何从现实世界到数据世界？

层次模型：像文档一样（各类noSQL），一对多。优势在于局部性，拥有文档的全部内容，缺点在于表示多对多及其复杂。

网络模型：图数据库，类似指针，复杂度较大。（顶点+表）（主-谓-宾）

关系模型：当前的主流，元组。



```txt
层次模型（一对多）──→ 网络模型（多对多）──→ 关系模型（范式化）
     │                    │                    │
  文档数据库            图数据库            关系型数据库
  (MongoDB)          (Neo4j等)           (MySQL/Oracle)
  局部性好            表达力强             通用性最强
  但难join            但生态小             但join成本高
```



关系性数据库的往往是强模式的，但图数据库与文档数据库，没有固定的模式，但应用程序使用时有隐式的模式（读/写）。



声明式 vs 命令式的对比暗示了一个深层规律：
你越"告诉系统要什么"（SQL），系统做自动优化的空间越大；你越"告诉系统怎么做"（命令式代码），灵活性越高但优化越难。



# 数据如何被存储与检索？

存储与检索，一体两面，数据结构决定了如何存储与检索。

按用途数据库大致分为：OLTP（事务型），OLAP（分析型），

按存储结构：日志结构存储引擎（hash、LSM-Tree），面向页的存储引擎（B-Tree）



从简单的一个txt文本追加写，并配上hash索引；

+分段，每段去重并排序

+每段进行合并

+内存中维护顺序，统一刷盘

+稀疏索引

我们得到了LSM-Tree（Log-Structured Merge-Tree）日志型存储结构，在这里没有原地更新，只有不断追加。LSM优点在于吞吐量，但事务等相关较弱。



B树则是典型的原地更新，WAL，关系性数据库的王者。

```txt
                    写入优先                    读取优先
                       │                          │
                  日志结构引擎                 B-Tree引擎
                  (LSM-Tree)                  (InnoDB等)
                       │                          │
              ┌────────┴────────┐          ┌──────┴──────┐
              │                 │          │             │
          Hash索引         SSTable      4KB页        WAL
        (Bitcask)       (排序+稀疏索引)  原地更新    预写日志
              │                 │          │             │
          不支持范围扫描    后台压缩合并   写放大较大    锁开销
```



索引：常见的是索引存值，多列索引。多维索引（空间），自动机（全文搜索，想起被有限状态自动机及KMP统治的恐惧了么？🤣）



对于分析型数据库：引入了列式存储、位图索引



最后，内存数据库快，不仅在于内存访问速度更快，更有基于内存无需磁盘的那一套数据结构访问开销。





# 如何跨系统传递数据？

笼统的将系统中的数据分为内存中的非自包含数据，与用于交互的自包含数据。

核心公式：

> **有意义的数据 = 数据本身 + 对数据的解释（Schema）**



| 格式              | 数据     | 解释                         | 特点               |
| ----------------- | -------- | ---------------------------- | ------------------ |
| JSON/XML          | ✅ 自包含 | ✅ 自解释（字段名在数据中）   | 人类友好，机器冗余 |
| Protobuf          | ✅ 自包含 | ❌ 需要共享 .proto 文件       | 极致紧凑，强契约   |
| Avro              | ✅ 自包含 | ❌ 读写Schema分离，靠Registry | 演化能力最强       |
| Java Serializable | ✅ 自包含 | ❌ 绑定JVM                    | 跨语言不可用       |

**演化的两个方向**：

- **向后兼容**（新代码读旧数据）：忽略未知字段
- **向前兼容**（旧代码读新数据）：缺失字段赋默认值

**数据传输的三条路径**：数据库共享、RPC/HTTP、异步消息——本质上都在解决"不同系统、不同版本间如何安全共享数据"。



# 集群如何复制数据？

为什么要从单机发展到集群？

```txt
单机瓶颈
  ├── 容量不够 → 分区（数据分散到不同节点）
  ├── 吞吐不够 → 复制（多副本分担读）+ 分区（多节点分担写）
  ├── 可用性不够 → 复制（一个挂了另一个顶上）
  └── 延迟太高 → 复制（地理就近部署）
```

集群最大的代价：部分失效，失去了原子性。

所有复制的难点都在于：正在被复制的数据，时刻都是变化的。

```txt
主从复制（最主流）
  ├── 同步：强一致，但性能差，一个从挂全挂
  ├── 半同步：一个同步+其余异步（实用折中）
  └── 异步：性能好，但有复制滞后 → 最终一致性
        ├── 读自己的写（从主库读）
        ├── 单调读（固定读同一副本）
        └── 前缀一致读（分区内有序）

多主复制（多数据中心/离线场景）
  ├── 核心难题：冲突解决
  │   ├── 避免冲突（按地域路由）
  │   ├── 收敛一致（LWW（last write win）/合并/保留冲突）
  │   └── 无冲突数据类型（CRDT）
  └── 拓扑：环/星/全对全

无主复制（Dynamo风格）
  ├── Quorum：w + r > n
  ├── 读修复 + 反熵
  └── 版本矢量（happen-before vs 并发）
```

这章最后部分的happen-before 与 并发的讲解特别有意思，值得反复观看。

目前核心系统，通过oceanBase，分区+复制，即获得冗余，又增加了容量与吞吐。



# 数据如何分片？

分区的目的是**负载均衡**，但引入了两个新问题：

**问题1：如何决定数据去哪个分区？**

| 策略           | 优点         | 缺点               |
| -------------- | ------------ | ------------------ |
| 关键字范围分区 | 范围查询高效 | 热点（如按时间戳） |
| 哈希分区       | 分布均匀     | 丧失范围查询能力   |
| 热点加随机后缀 | 打散热点     | 读取需查所有后缀   |

**问题2：二级索引怎么办？**

- **基于文档分区**：每个分区独立维护二级索引（写简单，读需 scatter-gather）
- **基于词条分区**：按索引值范围分区（读简单，写放大严重）

**再平衡策略**：固定分区数迁移 > 动态分裂合并 > 按节点比例。拒绝 mod。



# 数据库事务是什么？

整体上：事务的目的是简化编程模型。无处不在的抽象，屏蔽底层的复杂，给上层一个简单的抽象。

ACID：C是目的，AID是为了实现C所提供的功能。

```txt
读已提交 (RC)
  ├── 解决：脏读（读到未提交数据）
  └── 解决：脏写（覆盖未提交写入）
        │
        ▼
可重复读 / 快照隔离 (RR/SI)
  ├── 解决：不可重复读（MVCC快照）
  ├── 解决：更新丢失（SELECT FOR UPDATE / CAS）
  └── 未解决：写倾斜（幻读）
        │
        ▼
串行化 (Serializable)
  ├── 解决：写倾斜（先读后写，判断条件已失效）
  └── 实现方式：
      ├── 严格串行执行（Redis单线程/存储过程）
      ├── 两阶段锁定 2PL（读锁+写锁，性能差）
      └── 可串行化快照隔离 SSI（乐观，提交时检测冲突）
```



值班医生场景——"先查是否还有其他人值班，再决定是否下线"。在 RR 下，两个事务同时查到"还有2人"，同时下线，结果0人值班。



# 从单机到分布式的挑战？

> **在分布式系统中，你无法区分"对方挂了"和"网络断了"。当观察与感知变得不可靠时，如何获取有效知识并用于判断？**

三大不可靠：

| 不可靠       | 表现                             | 应对                                    |
| ------------ | -------------------------------- | --------------------------------------- |
| **网络**     | 超时≠失败，可能只是慢            | 动态调整超时；传 Deadline 而非 Duration |
| **时钟**     | 日历时间回拨；单调时间不可跨节点 | 逻辑时钟（Lamport）；不依赖时间戳排序   |
| **进程暂停** | GC/上下文切换导致租约失效        | Fencing 令牌（单调递增编号）            |

Fencing 令牌：

> 节点A获取锁 → 令牌=33 → GC暂停 → 锁过期
> 节点B获取锁 → 令牌=34 → 写入数据库
> 节点A恢复 → 用令牌=33写入 → 数据库发现 33 < 34 → 拒绝！



多数仲裁：单个节点无法判断自身状态，只能依赖法定票数。这是后面所有共识算法的基础。



# 集群如何达成共识？

**两个容易混淆的概念**：

|        | 可线性化 (Linearizability) | 可串行化 (Serializability) |
| ------ | -------------------------- | -------------------------- |
| 管什么 | 单个对象的单次操作         | 跨多对象的事务             |
| 要求   | 表现得像只有一份数据       | 等价于某种串行顺序         |
| 时序性 | 有（实时序）               | 无（只要求存在某个顺序）   |
| 组合性 | 不保证组合原子性           | 保证事务内所有操作原子     |

> **Socratic 追问**：你笔记中问了一个极好的问题——"线性化是局部，可串行化是整体"。那么，**一个系统同时满足线性化和可串行化，就是"严格可串行化"（Strict Serializability）**。2PL 和实际串行执行满足它，但 SSI 不满足（因为从快照读，不满足线性化）。你能想到为什么 SSI 不满足线性化吗？（提示：事务 T1 在 t=1 创建快照，t=5 才提交。在 t=3 时另一个事务 T2 读同一个 key，读到的是 T1 之前的旧值——但 T1 的操作在 t=1 到 t=5 之间"看起来"已经生效了。这违反了线性化的实时性要求。）

**共识的层次**：

```txt
因果一致性（偏序）
  └── Lamport 时间戳 → 全序，但无法做即时决策
        └── 全序广播（原子广播）→ 所有节点收到相同顺序的消息
              └── 共识算法（Raft/Paxos）= 全序广播 + 同步复制
                    └── 线性一致性
                  
```

总结：

Lamport 时间戳提供逻辑排序；
全序广播要求共同顺序；
共识算法通过多数派同步复制实现共同顺序；
线性一致性还需要共同顺序尊重真实时间，并且读写都基于已提交状态。



**2PC 的致命缺陷**：协调者单点 + 同步阻塞。参与者持有锁等待协调者恢复——这是"分布式噩梦"。

**CAP 定理的正确理解**：

> 分区容错没得选（网络总会断），我们只能在**发生分区后**，在一致性与可用性之间做选择。



# 什么是派生数据系统？

**一个复杂系统不会只用一种数据库。记录系统 + 多个派生数据系统，如何整合为一个逻辑整体？**

```txt
记录系统（System of Record）
  │
  ├──→ 批处理 ──→ 派生数据（搜索索引/数据仓库/ML特征）
  │
  ├──→ 流处理 ──→ 实时派生（缓存/物化视图/告警）
  │
  └──→ CDC ────→ 跨系统同步（ES/Redis/数据湖）
```



# 什么是批处理？

```txt
Unix管道（单机）
  cat | awk | sort | uniq -c | sort -r | head
  核心：顺序IO > 随机IO（sort外部排序 vs Python散列表）
      │
      ▼
分布式文件系统（HDFS）
  核心：把计算调度到数据所在节点（数据不动，代码动）
      │
      ▼
MapReduce
  Mapper → 按key排序/混洗 → Reducer
  Join/GroupBy 在 Reducer 阶段完成
  限制：每个MR必须全部落盘才能启动下一个
      │
      ▼
数据流引擎（Spark/Flink）
  整个作业是一个DAG，无需等前一步全部完成
  更灵活的执行模型
```

这里的批处理是全量输入到全量输出，核心系统的批处理更像是：输入-轮询数据库-输出，更像是流处理的退化。



# 什么是流处理？

**与批处理的本质区别：输入无界，没有"结束"的概念。**



消息的传递：

```txt
无代理（ZeroMQ）──→ 直接TCP，无持久化
      │
消息代理（JMS/AMQP）──→ 队列，消费后删除，负载均衡
      │
基于日志（Kafka）──→ 分区，偏移量，持久化，可重复消费
      │              天然fan-out，但分区决定并行度
      ▼
CDC（变更数据捕获）──→ 捕获数据库binlog作为事件流
      │                初始快照 + 增量日志
      ▼
事件溯源 ──→ 记录业务事件（有语义），而非数据变更
              命令→事件，事件不可拒绝
```

> 数据库是日志真相的缓存，不可变事件比最终状态包含更多信息。



流处理的三大难题

**1. 时间推理**：

| 时间类型             | 问题                              |
| -------------------- | --------------------------------- |
| 处理时间（机器时间） | 重新部署→事件堆积→统计失真        |
| 事件时间             | 延迟、乱序、需要水印（watermark） |

**2. 流的连接**：

| 连接类型 | 输入              | 状态               | 时间依赖             |
| -------- | ----------------- | ------------------ | -------------------- |
| 流-流    | 两边都是无key事件 | 窗口缓冲区（有限） | 有窗口               |
| 流-表    | 事件 + CDC        | CDC侧全量快照      | 无窗口               |
| 表-表    | 两边都是CDC       | 双向全量快照       | 无窗口，最新join最新 |

**3. 容错**：

批处理可以重跑（输入固定），流处理不行（输入无界）。解决方案：

- 微批/存档点（checkpoint）
- 原子提交输出
- **幂等写入**（你笔记中提到的核心系统异步任务，如果重试不幂等，就是灾难）
- 失败后状态重建



# Trade-Off

全书 12 章，所有的技术选择都可以归结为以下几组 trade-off：

| 维度         | 左               | 右                | 你的判断                   |
| ------------ | ---------------- | ----------------- | -------------------------- |
| 写入 vs 读取 | LSM-Tree（写快） | B-Tree（读快）    | 核心系统读多写少→B-Tree    |
| 灵活 vs 效率 | JSON（自解释）   | Protobuf（紧凑）  | 跨系统用JSON，内部用二进制 |
| 一致 vs 可用 | 同步复制/2PC     | 异步复制/最终一致 | 金融→一致优先              |
| 简单 vs 性能 | 单机/垂直拓展    | 分布式/水平拓展   | "强大的虚机 > 一堆容器"    |
| 全量 vs 增量 | 批处理           | 流处理            | 核心系统→增量为主          |
| 抽象 vs 控制 | 声明式SQL        | 命令式代码        | AI时代→声明式更有价值      |
