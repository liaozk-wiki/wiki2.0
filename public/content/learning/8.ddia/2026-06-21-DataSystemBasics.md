# 可靠、可拓展、可维护

数据密集形系统的通用结构：

1. 数据库（oracle、oceanbase）
2. 缓存（redis，java常量）
3. 索引（核心系统好像没这个？es等，日志算是一个）
4. 流式处理（消息异步处理？太多了，契约到核保，核心到医保通。但流式不等同于异步消息）
5. 批处理（专门的批处理服务，各类定时任务）



## 可靠

即使存在某些故障，系统依然可用。尤其金融系统，可靠性是重中之重，甚至是唯一，可以慢，但绝不错。

> 类似：上周核保事件处理服务挂了，恢复后，一个严重的问题就是因为时间差异，导致所有的核保件都被判断为核保暂缓，最后不得已全部人工干预。这其实是一个严重漏洞。当然这个是人为的错误，应该要通过流程避免



硬件故障：磁盘->RAID，双电源，南北中心灾备

软件故障：某个服务崩了，没有什么办法避免，只能充分的测试，隔离，监控等（对账等等），不可能有没有bug的软件。（系统中各个部分的兜底策略）



## 可拓展

系统以某种方式增长，我们应对增长的措施有哪些？如何添加计算资源来处理额外的负载？



负载：如何描述负载？

QPS、TPS等，也可以是数据库的写入比例，同时活跃用户数，缓存命中率，平均值，峰值等

twitter的例子：

1.发帖子：关系型数据库查询 到 更新缓存，瓶颈在于查询数据库压力

2.发帖子：直接更新到每个用户的时间线缓存，瓶颈在于写入，需要向所有关注者的缓存队列写入



性能：

1.假设负载增加，此时系统资源不变，会发生什么？

2.假设负载增加，要求性能不变，又需要增加多少系统资源？



描述性能：可以是吞吐量，也可以是响应时间，p50，p95，p99等

监控：10min的滑动窗口，来计算响应百分位数

虽然主流总是在强调微服务，强调无状态服务水平水平拓展，有时几个强大的服务器，仍然比大量的虚机更简单，更便宜。有状态服务的拓展比较麻烦，一般操作：数据库单独一个节点，垂直拓展，知道不得已才水平拓展（不过oceanbase之类天然的分布式数据库）

负载高度不可预测，自动弹性拓展也就越有效。



## 可维护

运维，简单（对复杂性的抽象），可演化



总之一个系统，必须完成预期的多种需求：功能需求、非功能性的（可靠、拓展、运维等等）

# 数据模型与查询语言

软件的一切是构建在抽象的基础上：现实世界--数据结构/模型--数据世界。

数据模型：

业务语义下的数据模型是对现实世界的抽象

数据世界中也有数据模型，如通用数据模型（XML，JSON，数据库中的表，图等），抽象的维度更高，也更通用，不与具体业务背景绑定

软件开发中的万能钥匙：没什么是包一层解决不了的（抽象：提供更简洁的数据模型来隐藏复杂性）



## 关系&文档

早期对数字世界通用模型的建模有：层次模型（一对多）、网络模型（多对多，但类似指针，巨复杂）、然后是关系模型（元组，关系就是表）。

文档数据库=层次模型

图数据库=网络模型

简历：

1. 一个json=一个文档=层次模型，但很难表示多对多，有大量冗余，很难join
2. 关系：基于范式，不停拆分，但需要查询一个简历时，往往需要许多join许多表

表示多对一和多对多时：关系与文档 都是通过标识符

文档的优势在于局部性，因为将相关数据存放在一个文档内

多年实际的开发中几乎就没碰见过文档数据库，关系型主宰一切，所以也只能是一个模糊的概念



多对多的关系是不同类型之间的一个重要区别，只有一对多，或者没有关系，文档数据库最合适。

# 数据存储与检索

应用层面，数据库其实只干两件事儿：存进去，读出来。

数据库又可以区分为：

1. 按照用途：事务型，分析型
2. 按照底层数据存储方式：日志结构存储引擎（hash、LSM-Tree），面向页的存储引擎（B-Tree）

一个极简的数据库：

```shell
#! /bin/bash
db_set() {
	echo "$1,$2" >> database
}
db_get() {
	grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}
```

使用的是日志追加写的方式，写入性能极佳，但读取性能垃圾。





## 索引

索引均是基于原始数据派生而来的辅助数据结构。



### 哈希索引

这里我们以Bitcask为例，非常简单与精巧。



数据格式：K-V

物理结构：所有数据的存储全部采用追加式（与前面的极简数据库一致），即最终文件中包含相同key的多个不同版本的value。

此时索引：存放在内存中的hashMap，key = K，value = V在磁盘文件中的偏移量。

一次寻址就可以从磁盘加载到内存，如果担心撑爆磁盘（太多更新，导致日志中有大量的历史版本），就将日志文件拆分成多个段，启用新段时，可以对旧段进行压缩合并。

最大的局限就是不支持范围扫描



### SSTables&LSM-Tree

SSTable（Sort String Table，许多NoSql的磁盘文件格式Kafka等） 相比于前面的追加日志写，新增限制：key不能重复，且数据存储严格按照key排序，不能默认追加写入。



仅就数据结构上的这一调整，相比前面的hash索引追加日志写的结构：

1. 合并段更简单高效，类似merge sort
2. 因为有序，所以不需要为每个key创建索引，只需在内存中维持一个稀疏的索引即可
3. 多个KV写入一个块，稀疏索引指向块头，写入前压缩，即减少磁盘占用，也减少读取时的IO带宽占用

这里的压缩：例如利用排序，进行前缀压缩

![image-20260530153716213](https://markdownupload.oss-cn-chengdu.aliyuncs.com/md/20260530153723523.png)

利用廉价的cpu来换取宝贵的IO开销。



LSM-Tree（Log-Structure-Merge Tree）：

一种存储引擎，底层落盘的文件结构是SSTable

因为写入可能是任意顺序的，而落盘则要求排序，故可以在内存中维护有序的数据结构例如B树，当一定大小时，就批量落库。将随机写，转为顺序写。

同时为了防止崩溃落库，再添加一个记录的追加日志。

总之SSTable的一个核心要点就是：落了盘的数据，基本不再变化，除了合并或整理归档。

LSM-Tree与B+树的最大区别除了底层数据结构外，表现形式就是：B+树存在更新操作，需要找到数据，然后覆盖，但LSM-Tree 则不存在，对数据的所有增、删、改 都是 追加写。同一个key SSTable1，SSTable2，SSTable3 均有副本，但后台会合并压缩整理。

Lucene就是采用这种。





### B-Tree

关系型数据库的统治者。

日志结构索引是将文件拆分成多个可变大小的段，而B树这是固定大小的4KB页，页是物理结构中读写的最小单元。

关于B树的结构不再过多描述：

WAL 预写日志：先写日志再更新页

原地更新：锁



对B树的一些优化：

1. 不在覆盖页+维护WAL，而是写时复制（常见的fork、mvcc等）
2. 压缩键
3. 叶子添加指针（B+树）
4. 分形树（root节点搞一个buffer，追加写，然后异步下推更新数据，写入效率极高，查询就比较麻烦）



### B树与LSM树的对比

LSM：极致的写入效率。B树需要一次WAL写，一次页的写入。

写时放大：LSM比B树小

LSM：异步的压缩与合并占用额外磁盘IO，同时也会影响查询。因为不存在副本，B树对事务支持更好。



### other

1. 索引存储值：innodb的聚集索引
2. 多列索引（级联索引）
3. 多维索引（R树，空间数据结构，也是root到叶子的树，只是没有排序，只有包含，同时依据MBR来确定包含）
4. 全文搜索与模糊索引（lucene 自动机）



内存数据库：

1.与直觉不同，内存数据库的快，并不是因为他们不需要从磁盘读取，而是他们不需要使用写磁盘的格式对内存数据结构进行编码。（假设mysql数据结构全部在内存中，读取数据：root-4k页-对象-属性，但jvm中读取某个对象属性：基于偏移量直接读取内存中的地址）

2.除了性能外，内存数据库，可以提供更多的数据结构（优先级队列等）

3.内存数据库架构可以拓展到远大于实际内存的数据集（类似虚拟内存与交换文件）



NVM（non-volatile memory，如ssd等）技术得到广泛普及时：可能需要进一步改善存储引擎设计

### 列式存储

# 数据编码与演化



## 数据编码格式

业务总是在不停的变化，如何在系统创建之初更好的兼容未来可能的变化呢？

新的代码能读取旧格式的数据（一般比较简单），但旧代码还要能支持新的数据格式（允许旧版本）



系统一般包含两类数据表现形式：

1. 内存的中结构体/数组等，因为严重依赖当前进程上下文，通常有指针，故不是自包含。
2. 用于网络传输的自包含的字节序列，没有外部指针，一个字节序列包含了数据的全部内容（java的serializable）。

还有一类（自解释，甚至不需要了解数据的结构）

不同的编程语言有自己的将内存中的对象序列化为字节序列的方法，但针对跨系统，更通用的数据序列化：json、xml、二进制变体

json人类友好，但冗余太多，机器不友好

> **二进制编码（如 MessagePack）解析流程**：它采用 **TLV（类型-长度-值）** 结构。解析器读第一个字节，查表得知这是“整数”且“占用 4 字节”，然后直接拷贝接下来的 4 个字节到内存变量中。**不需要判断引号、不需要处理转义、不需要进制转换**。速度通常比 JSON 快 2~5 倍

> **Protobuf（极致的“自包含”，但放弃“自解释”）**：它体积最小、速度最快。但你看不到字段名，必须提前写好 `.proto` 文件，且收发双方必须用同一个协议版本

模式有动态生成，也可以与数据绑定，多版本共存。







Avro，读模式与写模式，及模式的演化

![image-20260621153003579](https://markdownupload.oss-cn-chengdu.aliyuncs.com/md/20260621153010496.png)



简单理解：数据要有意义，必然包含两类信息，一类是数据本身，一类是对数据的解释。

1. json 作为自解释数据结构，将两类信息整合在一起。
2. 内存中的数据，则通过类型或者结构体等代码中的定义来解释数据。
3. avro等二进制自包含数据编码则通过单独定义模式并在多个系统之间共享模式，来共享数据解释，然后仅传输数据，从而实现数据不仅能传输也能解释。



## 数据流模式

进程间的数据传输，将数据发送到非共享内存的另一个进程，如何将数据从一个进程传输到另一个进程？谁编码数据？谁解码数据？

1. 通过数据库：注意支持旧模式的代码，读取了新模式的数据，处理后写回时，写的是旧模式，导致新模式新增的数据丢失（核心系统的notify异步及backgroundcall异步，均属于这种类型。业务系统，插入调用目标与参数，单独的服务读取数据，进行处理。）
2. 通过服务调用：
   网络服务：http/soap（目前核心系统虽然有xml报文，但都不是soap，soap请求，必定有一个wsdl）
   RPC：核心系统存在RMI远程方法调用吗？ RPC传输的是二进制，不具备json一样的自解释，故要求发送方与接收方对对象的定义一致，是强契约的，否则会解析失败。
3. 通过异步消息传递：与rpc类似可以低延迟到另一个进程，同时也与数据库类似，不走http请求。可以缓冲，极大的解耦，自动重发，支持多个接收方，逻辑上发送与接收解耦。最大的差异在于单向。





## 演化

不管哪种传输数据的方式或者数据序列化的方式，模式的演化：

1. 基于旧模式的代码，能支持读取传输过来的新模式数据（向后兼容）
2. 基于新模式的代码，能支持读取旧模式下存储或者传输过来的数据（向前兼容）

向后兼容一般是忽略新的字段

向前兼容一般则是赋默认值

# 总结

首先是数据密集型系统的通用结构：数据库、高速缓存、索引、批处理、流式处理

其次是系统除了功能性需求（正确的实现业务需求，软件的第一性）外，还需要关注非功能性需求（软件领域）：可靠性（软件故障、硬件故障）、可拓展性（如何描述性能？p95，p99。twitter的消息演进。无状态服务的水平拓展（偶尔几个强大的虚机还是远远优于一堆小朋友），有状态服务则基本垂直拓展（数据库），）、可维护性（软件工程领域了）。



整体指标的总览之后，围绕着数据：

- 如何从现实世界抽象出数据模型？
- 抽象出的数据如何保存？
- 不同的系统之间数据如何传输？



1.如何从现实世界抽象出数据模型：

高纬度的抽象，最开始是层次模型，然后网络模型，关系模型。虽然后来关系型数据库统一了大部分，但层次模型-文档型数据库（mangodb等，文档数据库一般数据没模式，但应用程序往往假定数据有结构）、网络模型（图数据库）



2.抽象出的数据如何保存：

保存与检索密不可分（存进去、取出来），事务型，分析型：

日志结构：最简单的数据库K-V存储：一个txt文档，不停的追加写，读的时候取最后一条即可。为了更快的读取，内存构建hash索引。为了节约空间，再对文档段进行压缩与合并。再稍微进化一下，每一个文件段，新增要求内容按照key排序，同一个key每个文件段中只能出现一次。因为数据有序可以构建稀疏索引，后台再不断的合并小的SSTable，进行去重。LSM-Tree 内存中排序，然后落库SSTable到磁盘。以上就是日志结构数据库，没有更新，只有不停的追加写，还是顺序写，故写入效率极高。查询较慢，一般会配上布隆过滤器。

原地更新：B树结构的数据库，传统的关系型数据库大多这个结构。原地更新。事务性更强，查询也快。

全文索引--算法有限自动状态机

大数据：数据仓库，列式存储与压缩，位图索引



3.最后就是不同系统之间的数据传输（数据本身+对数据的解读）：

序列化：内存中的数据，依赖进程空间，无法跨进程传输，需要转换为自包含的字节序列（java有JMI，但这些绑定语言）。json、xml、及二进制变体（MessagePack（json 二进制，自解释）、Protobuf（依靠元数据+索引）、Avro （读模式，写模式）），无论哪种结构，均需要考虑演化（向前兼容/向后兼容）

传输：数据库、网络（http rpc）、异步消息




# AI总结

> 本文覆盖了 DDIA 前四章的核心脉络，从宏观的系统设计原则逐步深入到数据存储与传输的微观机制。
>
> **第一章：可靠、可拓展、可维护** — 这是数据密集型系统的三项非功能性基石。可靠性意味着故障下系统依然可用（硬件靠 RAID/灾备，软件靠测试与兜底策略）；可拓展性关注系统如何应对负载增长（用 p50/p95/p99 描述性能，用 Twitter 案例展示架构取舍）；可维护性则回归工程本质 —— 简单、可演化的系统才活得久。你补充的核保事件案例很好地说明了一点：**人为错误的危害远大于机器故障**，可靠性本质上是流程问题。
>
> **第二章：数据模型与查询语言** — 一切软件都在做"物理世界 → 数字世界"的建模。数据模型经历了层次 → 网络 → 关系 → 文档/图的演进，本质上是一对多 → 多对多 → 范式化的螺旋。文档数据库（MongoDB）牺牲了 join 能力换取局部性，图数据库则直接以节点和边表达复杂关系。你关于"AI 干掉了 step2（自然语言 → 代码），但 step1（物理世界 → 数字世界）的建模转换依然存在"的洞察非常精准 —— **抽象能力仍然是程序员的护城河**。声明式（SQL）与命令式（代码）的对比也暗示了一个深层规律：越"告诉系统要什么"，系统做自动优化的空间越大。
>
> **第三章：数据存储与检索** — 这是最硬核的一章，核心问题是"存进去怎么快，读出来怎么快"。两大类存储引擎：**日志结构（LSM-Tree）** 追求极致写入，后台异步压缩合并 SSTable，用顺序写替代随机写，写入放大远小于 B 树；**B-Tree** 则是原地更新，事务支持更好但受制于写入放大和锁开销。旁路还覆盖了 Hash 索引（Bitcask 的 K-V 映射）、聚集索引（InnoDB 的主键）、全文索引（Lucene 的有限自动机）、列式存储（数据仓库/位图索引）等。一个重要的纠正：**内存数据库的快不在于省了磁盘 IO，而在于不需要用磁盘格式去编码内存结构** —— 指针直接寻址 vs B 树逐页解析，这才是速度差的根源。
>
> **第四章：数据编码与演化** — 数据要在进程间流转，序列化是必经之路。自解释格式（JSON/XML）冗余但灵活；自包含但非自解释格式（Protobuf/MessagePack）高效但需共享 Schema；Avro 更进一步，把读模式与写模式分离，**靠 Schema Registry 在系统间共享"数据解释"**。关键能力是向后兼容（新代码读旧数据）和向前兼容（旧代码读新数据）—— 分别靠忽略新字段和赋予默认值实现。数据传输的三条路径（数据库共享、RPC/HTTP、异步消息），本质上都是在解决"不同系统、不同版本间如何安全地共享数据"这个问题。
>
> **贯穿全文的一条暗线**：所有设计抉择都是 trade-off —— 写入快则查询慢（LSM vs B-Tree），灵活则冗余（JSON vs Protobuf），抽象强则性能可控（SQL 声明式 vs 命令式）。理解这些取舍，比记住具体技术重要得多。
