# Derived Data System

一个复杂的系统，往往有不同的存储区、缓存、索引、分析系统。涉及将不同的数据系统整合到一起。

一个复杂的系统：

1. 记录系统+派生数据系统
2. 在线服务系统+离线批处理系统+近实时流处理系统



# AI总结

> 这篇笔记是 DDIA 最后一部分「派生数据系统」的总结，核心是：**复杂系统不会只用一种数据库，而是由记录系统+多个派生数据系统组成，关键在于如何用批处理、流处理、CDC 等方式把它们整合成一致的整体。**
>
> ---
>
> ### 1. 批处理
>
> - 本质是「时间换空间」：把原始数据通过离线计算，变成结构化派生数据供上层查询。
> - 对比 Unix 单机和分布式：
>   - Unix 管道利用 `sort` 等外部排序，顺序 IO 优于内存散列表的随机 IO。
>   - 分布式文件系统（HDFS）把计算调度到数据所在节点，减少网络传输。
>   - 作业编排器负责任务执行、资源管理、调度、DAG 工作流和容错。
> - **MapReduce**：Mapper → 按 key 排序/混洗 → Reducer。Join/GroupBy 在 Reducer 阶段完成。
> - **数据流引擎**：把整个作业当作一个 DAG，不必等前一个 MR 完全落盘才开始下一步。
> - 核心产出：派生数据 = 输入数据的衍生结果。
>
> ---
>
> ### 2. 流处理
>
> - 与批处理区别：输入无界、连续不断。
> - 事件是核心对象：小的、不可变的、自包含的记录。
> - 事件传递方式：
>   - 直接 TCP/管道/数据库轮询（无代理）。
>   - 消息代理（JMS/AMQP 风格）：队列、背压、负载均衡、扇出。
>   - 基于日志的代理（Kafka/Kinesis）：日志分区、偏移量、持久化、可重复消费。
> - **CDC（变更数据捕获）**：捕获数据库变更作为事件流，初始快照 + 日志压缩。
> - **事件溯源**：记录的是业务事件（有语义），而非仅仅是数据变更；命令转化为事件，事件不可拒绝。
> - **状态、流与不变性**：数据库是日志真相的缓存，不可变事件比最终状态包含更多信息。
>
> ---
>
> ### 3. 流处理的细节
>
> - 窗口类型：滚动窗口、跳动窗口、滑动窗口、会话窗口。
> - 时间推理：
>   - 处理时间（机器时间）不靠谱，重新部署会导致统计失真。
>   - 事件时间更准确，但需处理延迟、乱序、水印等机制。
> - 流的连接：
>   - **流-流连接**：两边都是无 key 事件，用窗口缓冲匹配（如搜索 + 点击）。
>   - **流-表连接**：一边是事件流，另一边是 CDC 物化出的全量维表快照。
>   - **表-表连接**：两边都是 CDC 流，物化为两张表，任何变化都重新计算结果。
> - 容错：
>   - 微批/存档点。
>   - 原子提交输出与副作用。
>   - 幂等写入。
>   - 失败状态重建。
>
> ---
>
> ### 4. 数据系统的未来
>
> - 数据集成：要么用分布式事务强一致（性能差），要么用 CDC 派生数据最终一致（主流）。
> - 分拆数据库：
>   - 联合数据库：统一读，一个查询可路由到多个存储。
>   - 分离式数据库：统一写，把写变成不可变事件，各数据库消费更新。
>   - 把批处理、索引维护、物化视图都看作数据流的一部分。
> - 端到端正确性：
>   - 不依赖中间件保证恰好一次，而在客户端/终端用操作标识符实现。
>   - 异步约束检查、先写后补偿。
>   - 数据不仅从设备到服务，也反向推送到设备。
>
> ---
>
> ### 总体总结
>
> 派生数据的实现两大范式：
>
> 1. **批处理**：输入有界，输出是输入的派生；MapReduce、DAG 引擎、分布式文件系统。
> 2. **流处理**：输入无界，事件为核心；消息传递、日志分区、CDC、事件溯源、窗口与连接、容错。
>
> 最终目标：把记录系统和多个派生数据系统，通过统一的数据流整合成一个逻辑整体。





# 批处理

批处理就是利用“时间换空间”的经典范式——当数据量大到无法在交互时间内完成计算时，我们就通过调度大量廉价机器，用几个小时的生命周期，将原始数据的“混沌”状态，规约为高度结构化的“派生黄金数据”，供上层实时业务直接查询。

传统的场景是一次请求/查询，返回对应的响应/结果。

需要处理的数据远大于一次交互式请求时——批处理（离线系统）：输出是输入的派生结果，一般不原地修改数据。



## unix单机上的批处理

```shell
cat /var/log/nginx/access.log | #1
  awk '{print $7}' | #2
  sort             | #3
  uniq -c          | #4
  sort -r -n       | #5
  head -n 5          #6
```



```python
from collections import defaultdict

counts = defaultdict(int) #1

with open('/var/log/nginx/access.log', 'r') as file:
    for line in file:
        url = line.split()[6] #2
        counts[url] += 1 #3

top5 = sorted(((count, url) for url, count in counts.items()), reverse=True)[:5] #4

for count, url in top5:  #5
    print(f"{count} {url}")
```



python维护了一个散列表，shell 则是对全部文本进行排序。

如果输入数据集（不重复的url）大于系统可用内存，shell更能高效利用（会将数百G文件分成几十个，分别处理再归并。散列表因为超出内存，每一条都需要磁盘随机io而不是 shell的顺序io）



## 分布式系统中的批处理

unix局限于单机，当数据大到单机磁盘放不下的时候，就需要分布式批处理



对于单机的文件系统由下到上的构成是：
1.驱动与磁盘直接交互，对象是块
2.块上面有页缓存
3.块api上文件系统，涉及node，目录等
4.文件系统之上则是操作系统统一的api



分布式文件系统类似：
1.块作为基础单元，通常数M到数百M
2.通过网络请求访问节点，机器上运行守护线程用于对外提供api服务
3.也会维护块位置，空闲块，目录，权限等元数据
4.类似虚拟文件系统，分布式文件系统提供dfs协议，将其作为一个整体来看待与操作



目前对象存储也能在一定程度上替换分布式存储，但是DFS（Distributed File System）具有：DFS 与对象存储另一个区别是：HDFS 等 DFS 可把计算任务调度到持有文件副本的机器上，让任务本地读文件，减少网络传输（当任务代码远小于待读文件时尤其划算）。对象存储通常把存储和计算解耦，虽然可能用更多带宽，但现代数据中心网络很快，通常可接受。同时这种解耦让 CPU/内存与存储容量可以独立扩展。



单机中的处理，需要进程执行不同命令，需要管道将一个进程的输出，作为另一个进程的输入，还需要给每个进程分配内存，调度cpu等等，这些是OS干的，同样分布式则是作业编排器（orchestrator）：

1. 任务执行器

2. 资源管理器

3. 调度器

   

一般的分布式任务处理涉及：

1. 资源分配
2. 工作流调度（DAG 有向无环图）
3. 故障处理（拉起来重新处理或者删掉重跑）



分布式任务的一大特点就是：允许将计算在实际存储数据的机器上调度，减少网络传输损耗。

map-reduce：mapper 映射，reduce 规约

1. 读取记录

2. map映射

3. key排序

4. reduce 按key处理

   

数据流引擎：

map-reduce ，需要将任务拆分为多个MR，每一个MR都涉及排序，涉及落盘，同时还需要每个MR全部完成后才能启动下一个MR。（一种隐式的工作流编排，对于系统来说只有多个独立的MR任务）

数据流引擎则没有这么多限制，整个任务当作一个整体，无需上一步全部就位才开始下一步。

# 流处理

> 一个复杂的系统总是从可用的简单系统演化而来的，从0开始设计的复杂系统从来都用不了。



批处理的输入是有界的，流处理则是无界的。



## 传递事件流

文件流的处理，是将字节序列解析为记录。

流处理的基本对象是事件：一个小的、自包含的、不可变的对象，包含某个时间点发生的某件事情的细节



批处理，输入可被多个作业处理。流处理，生产者生成事件，多个消费者进行处理，相关事件聚合成主题。

（可以近似的将核心系统诸多异步任务理解为流处理，生成记录，存储到数据库，其它服务，定期轮询抓取并处理，相比MQ主要区别在于，对延迟的容忍性）





### 消息传递

一说到消息，总是想到MQ，但仅就生产者-通道-消费者（发布-订阅） 这个模型而言，除了mq，基于数据库传输的两个程序，基于tcp/管道 连接的两个程序，也都属于。

如何区分不同的消息传递系统？

1. 如果生产者发送消息的速度比消费者能够处理的速度快会发生什么？a.丢弃，b.队列（队列如何增长？队列装不进内存时如何处理？队列如何与磁盘交互？），c.背压（tcp流量控制）

2. 集群的节点崩溃了会发生什么？是否会消息丢失？

   

组件的很多特性目的之一就是简化编程模型。



生产者通过网络直接将消息发送给消费者：

1. 无代理的消息库，如 ZeroMQ 和 nanomsg

2. 消息代理：就是大家说的MQ，针对消息流而优化的数据库，作为服务器，生产者与消费者作为客户端，生产者写入，消费者读取。通过将数据放在代理上，来解决连接和持久化的问题。



消息代理与数据库的区别：持久、数据集大小、新数据感知



多个消费者消费时：负载均衡，fan-out扇出（发给所有人）

![ddia_1101](https://ddia.vonng.com/v1/ddia_1101.png)





确认与重传，这里有一个隐蔽的问题：使用负载均衡时，消息是abc，但b没有ack，重传给其它消费者后，实际消费顺序变成了acb。





### 分区日志

传统消息代理，默认被消费后删除消息。而磁盘文件则是除非显式删除否则均保留，二者的结合=基于日志的消息代理。

生产者向日志追加写，消费者读取日志。为了增加吞吐与水平拓展，再将日志分区，主题就是分区的集合，每个分区内维持一个单调递增的序列。（kafka，Amazon Kinesis Streams）



基于日志的代理与传统代理：天然支持fan-out，但以分区来分配负载有2个天然弊端：1.分区决定了并行度，2.毒丸消息，会阻塞后续所有消息的消费



偏移量：当作主从日志同步，消息代理是主库，消费者是从库



磁盘：日志基本会被分段，一段时候后过期或者转储。



基于日志的消息代理更像批处理，固定的偏移量，作为输入，可以重复消费。



## 数据库与流

流的处理对象是一个事件，事件代表着一条记录。对数据库的写入也是一个事件，所有对数据写入的事件记录起来就是一个完整的事件流。（binlog，数据复制，状态机复制）





### 保持数据同步

一般多个存储系统之间通过elt批量转储，周期性转储太慢就会采用双写，双写带来的问题是：

1.数据竞争，导致不一致。修改顺序不一致

2.一成功，一失败，导致数据不一致



分布式锁+失败补偿 可以解决，但没有那么优雅，更合理的结构是：捕获业务数据库的变更，产生事件，通过事件去同步各个系统。



### 如何捕获数据变更？

change data capture, CDC：数据变更捕获使得系统存在一个主库是领导者，其它则是追随者。

初始快照+日志压缩，有些数据库提供变更的流式API





### 事件溯源

CDC记录的是数据库数据的变化，没有业务语义。事件溯源是记录的是那些导致数据变化的事件，有业务语义。

命令转化为事件，事件意味着数据变更，不允许拒绝事件，更改用户名这类，发事件时就需要确保不会失败。







### 状态、流和不变性

批处理的输入是不变的，输出则是输入的衍生数据。

流处理中，尤其是涉及到数据库CDC流，这里某个时间段的事件也是不变的，虽然作为事件响应的数据库状态会随着事件而变化。数据库变成了事件响应的最终结果或者是缓存。

> 事务日志记录了数据库的所有变更。高速追加是更改日志的唯一方法。从这个角度来看，数据库的内容其实是日志中记录最新值的缓存。日志才是真相，数据库是日志子集的缓存，这一缓存子集恰好来自日志中每条记录与索引值的最新值。



不可变事件，包含了比最终状态更多的信息



通过对事件流的不同消费，可以获取不同的视图，一些针对读优化，一些针对写优化，即使新增组件也仅新增对事件流的消费。



事件溯源+CDC 一大弊端就是：异步消费。会导致数据不一致。一种解决：将事件写入日志的时候，同步更新读视图（需要事务，如果读视图与日志横跨系统，需要分布式事务）

事件的设计也能简化并发，将原本的多条数据库更新变成单个事件的写入。

如果分区3中的事件仅会更新分区3中的应用，单线程日志消费者也不需要并发控制



永远保持所有变更的不变历史，可行性取决于数据集的流失率(变化速度)



## 流处理

前面是流的产生、传输，此刻则是处理。



1. 用于与其它系统进行数据同步

2. 发邮件、通知等等，用作业务处理

3. 将一个或多个流作为输入，处理后产生一个或多个流作为输出



处理流以产生其他衍生流。处理这样的流的代码片段，被称为 **算子（operator）** 或 **作业（job）**。

与批处理中的流式处理最大的区别，流处理数据无界，所以没有排序。也无法使用重跑来实现容错。





### 流应用

1. 复合事件，从输入中筛选出符合特定查询条件的事件，发现就发出一个复合事件

2. 监控分析，譬如统计时间窗口内的平均值

3. 维护物化视图（同步数据）

4. 消息传递与RPC



### 时间推理

过去5分钟的平均值，如何统计？——处理的机器上的时间，事件产生时的时间，没有全局事件，还涉及延迟阻塞。



使用机器时间：重新部署流处理器，事件积累，此时的统计其实不正确。

使用事件时间：无法确认是否所有事件都到达了（忽略、更正窗口、特殊消息，告知不会有比xx时间更早的消息了）

离线设备，可能时间设置的不正确



窗口：

1. 滚动窗口：时间戳在 `10:03:00` 和 `10:03:59` 之间的事件会被分组到一个窗口中，`10:04:00` 和 `10:04:59` 之间的事件被分组到下一个窗口

2. 跳动窗口：也是固定窗口，但前后允许部分重叠

3. 滑动窗口：不断的进出

4. 会话窗口：用户登录的会话



### 流连接

如何将多个流拼装在一起？流-流，流-表，表-表



流-流连接：

搜索是一个事件，都搜索结果的点击又是一个事件，二者是有关联的，一般通过会话id连接。



流-表连接：

活动流，包含用户id，用户表存在数据库。可以将流-表连接中的表理解为一个关于表的变更事件流，新的数据会覆盖旧的数据（不保留历史状态，仅保留最新状态的流，流流连接一般有时间窗口，流表连接的表一般是无限时间窗口（可以看所有key））。同时输入的流也不需要维护一个窗口用于匹配，来了就匹配表。



表-表连接：

流是表的变化，表是流的快照。流-流连接，是有时间段的，表-表连接，没有时间段，都是用最新的连接最新的。推特例子是将查询结果物化到缓存:

```sql
SELECT follows.follower_id AS timeline_id,
    array_agg(tweets.* ORDER BY tweets.timestamp DESC)
FROM tweets
JOIN follows ON follows.followee_id = tweets.sender_id
GROUP BY follows.follower_id
```



流处理则是两个表的任何变化，都会重新计算全量数据，并更新结果集合。



如何精准区分这三类中的“流”与“表”？

关键指标看两点：**① 是否携带主键（Key）和操作类型（±）？ ② 状态存的是窗口还是全量？**

| 连接类型      | 输入数据性质                                 | 状态（State）存储的内容                 | “表”存在吗？                                                 |
| ------------- | -------------------------------------------- | --------------------------------------- | ------------------------------------------------------------ |
| **流-流连接** | 两边都是 **仅追加（无主键，无删除）** 的事件 | **窗口缓冲区**（有限时长，过期即删）    | **不存在**。只有“临时窗口”，没有“全量表”。                   |
| **流-表连接** | 一边是仅追加事件，**另一边是 CDC（有主键）** | 存 **CDC 那一边的完整全量快照**（字典） | **存在**。由 CDC 流物化出的“当前维表快照”。                  |
| **表-表连接** | **两边都是 CDC（均有主键和操作类型）**       | **存两边的完整全量快照**（双向字典）    | **存在**。两边都是由 CDC 流物化出的“当前快照表”，彼此相互驱动。 |

## 端到端正确性

# 总结

首先我们得理解派生数据，任何一个业务系统，有其记录数据，记录的是具体业务的状态。派生数据则是基于这些原始的一手记录，经处理，衍生的数据库。

实现派生数据的两大方式分别是：

批处理：重点介绍了map-reduce 与 分布式处理。不仅文件的存储是分布的，对分布文件的批处理也是分布的，通过调度，每个服务器处理自己所拥有的数据。

流处理：首先介绍了流处理的对象——事件。然后是事件的传递（无代理的网络，有代理的JMS风格与日志类型）。再进一步通过CDC捕获数据库变更的事件，以此来实现跨系统的数据同步。然后引出事件溯源与流作为表的变更，表作为流的快照。最后再到真正的流处理，涉及时间与窗口、流的连接、及流处理中的容错机制。

最后是对数据系统未来的一些展望：

1. 通过流式处理与批处理结合，来实现记录数据与衍生数据的同步，从而构建一个完整的数据层。
2. 多种数据存储技术结合，联合数据库统一读，分离数据库统一写，围绕数据流设计派生系统，及观察派生数据系统从数据的写入经层层处理到读取。
3. 端端正确性，不再依赖底层组件的抽象，从源头实现数据的正确性
