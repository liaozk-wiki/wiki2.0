# DistributedDataSystem

# AI总结

本文是 DDIA 第二部分「分布式数据系统」的读书笔记，核心围绕一个命题展开：**当数据量大到单机无法承载时，如何用多台机器组成一个逻辑整体对外提供服务？** 代价是复杂度的急剧上升。

全篇按层次递进展开：

1. **数据复制（多副本）**：主从复制（最主流，同步/异步/半同步）、多主复制（多数据中心/离线场景，核心难点是冲突解决）、无主复制（Dynamo 风格，quorum 机制，版本矢量与并发判定）。所有复制机制的难点都在于「被复制的对象时刻在变化」。异步复制必然带来复制滞后，需在应用层处理：读写分离、单调读、前缀一致读。

2. **数据分区（分片）**：关键字分区、哈希分区、二级索引分区（基于文档 vs 基于词条）。再平衡策略：固定分区数迁移、动态分裂合并、按节点比例分区。服务发现是典型的三层路由问题。

3. **事务**：事务是简化应用层编程模型的抽象。隔离级别从低到高依次解决：脏读 → 脏写 → 不可重复读（MVCC 快照隔离）→ 更新丢失（SELECT FOR UPDATE/CAS）→ 写倾斜（幻读，需串行化）。串行化实现方式：单线程执行、两阶段锁定（2PL）、可串行化快照隔离（SSI）。

4. **分布式系统的麻烦**：网络不可靠（超时难定）、时钟不可靠（日历时间回拨、单调时间不可跨节点，应使用逻辑时钟）、进程暂停（GC/上下文切换导致租约失效）。解决方案：多数仲裁 + fencing 单调递增令牌。

5. **一致性与共识**：线性一致性（表现得像单副本）≠ 可串行化（事务等价于某种串行顺序）。CAP 定理下，发生网络分区时只能在一致性与可用性之间取舍。因果一致性是偏序，Lamport 时间戳提供全序但不解决即时决策，全序广播（原子广播）才是分布式排序的基础。共识算法（Raft/Paxos）等价于全序广播 + 同步复制，是实现容错一致性的基石。2PC 因协调者单点和同步阻塞存在严重性能问题。



# 分布式数据系统

第一部分是单台机器上的数据存储与检索，重点在于如何从现实世界抽象到数据世界，然后实现数据世界的存储与检索，最后则是数据在不同机器之间的传输。

第二部分则是随着数据进一步增加，我们需要多台机器作为一个逻辑上的整体来提供存储与检索服务。此时面临的新的挑战是：

1. 拓展，需要将负载分散到不同的机器
2. 容错与高可用，挂了某一个还是能继续运行
3. 延迟考虑，总是希望能就近访问



拓展：

- 垂直拓展：共享内存架构，共享磁盘架构。
- 水平拓展：多节点。复制-分区



# 数据复制

可能出错的事物与不可能出错的事物之间主要的区别在于不可能出错的事物一旦出错往往意味着不可修复。



数据复制：多台机器有着相同的副本。

1. 更强大的吞吐量——负载均衡
2. 冗余备份——高可用
3. 地理上更接近——降低网络延迟

主从复制、多主节点复制、无主节点复制。同步复制、异步复制。如何处理失败的副本，最终一致性，复制滞后，读自己的写，单调读等等。



所有复制的难点均在于如何处理被复制的目标对象是时刻处于变化的。



## 主节点与从节点

1. 主副本写入
2. 从副本只能读
3. 主从之间通过日志或者更改流进行同步



同步复制：主节点写完后，需要副节点同步完成后，才视为写入完成。优点：互为备份。缺点：性能下降

半同步：一个副节点同步复制，其余副节点异步复制。同步复制节点性能下降或失败时还能将异步复制节点选一个提升为同步复制节点。

全异步：可能数据丢失，但吞吐性更好。

链式复制：同步复制的变体，头部写，尾部读。



### 配置新的从节点

最简单的当然是直接暂停主数据的写，然后复制数据，哈哈。

一般：

1. 某个节点的副本快照，复制到新的节点
2. 通过日志同步后续的修改



### 节点失效

从节点失效：重启后，日志同步

主节点失效：

1. 选举新的节点
2. 应用切换到新的节点
3. 原主节点活过来后，需要被告知是从节点了

Q：

1. 异步复制，新的主节点不是最新的，旧的主节点重新上线，可能导致新的主节点收到有冲突的写（来自应用+来自旧的主节点同步），丢弃旧主节点未同步的日志，会造成数据丢失
2. 从节点提升为主节点后，自增主键使用了之前主节点已经分配过了的主键，而之前的数据，已经同步给redis，导致，redis与数据库不一致。因为涉及第三方，丢弃数据变得非常危险。
3. 脑裂：特殊情况下，两个节点均认为自己是主节点。
4. 如何设置合适的超时来检测主节点存活？太长--需要更长的时间恢复，太短--不必要的切换。

只有trade-off，没有终极答案



### 复制日志

1. 基于sql语句：需要额外考虑`now(),rand()`及触发器等，用的少了
2. 基于预写日志：pg、oracle
3. 基于行的逻辑日志：binlog
4. 基于触发器，通过程序进行同步





## 复制滞后

异步复制——最终一致性

1. 基于业务逻辑从主库读&基于更新时间选择读的库。a设备写，b设备读...
2. 单调读，弱于强一致，比最终一致要好，连续多次读，默认同一个副本。
3. 前缀一致读，默认按照写入的顺序读，但分区独立运行，不存在全局写入顺序（分区内有序，但分区间无序）。导致answer先于question。

复制滞后的解决，可以通过应用层来处理，而不是严格依赖数据库本身。开发人员：当延迟增加了后，应用程序的行为是否符合我们的预期？







## 多主节点复制

主从复制的自然拓展就是配置多个主节点，每个主节点集群内部主从复制，多个主节点之间一般是异步复制。



场景：

1. 多数据中心。
2. 离线客户端操作（手机上的日程记录）
3. 协作编辑，类似多主节点复制



多主复制相比于主从复制最大的变化就是：需要解决主节点之间的冲突。

1. 避免冲突，中国的总是写入中国数据中心，北美的写入北美数据中心
2. 收敛于一致，多主同步，不存在一致的写入顺序：a.基于id，会数据丢失；b.多个值合并；c.保留冲突信息，事后应用解决
3. 自动冲突的解决方案：无冲突数据类型、可合并的数据结构、操作转换算法



一般多主节点的同步拓扑结构（想到了x86与arm之间的不同的内存同步结构🤣）：

1. 环状
2. 星形
3. 全部-全部 （常见）

星型与环状：需要标识符防止重复转发，同时某个节点坏了会影响其他节点

ALL-ALL：因为延迟，容易出现覆盖。先发生的因为延迟同步，覆盖了后发生的。写操作的因果排序。







## 无主节点复制

这里其实有一点像是完全的分布式算法了。

Dynamo 风格数据库：

n个节点，写入w个就算成功，读取时需要读取r个节点的数据。一般w=r=(n+1)/2。w + r > n（读写quorum法定人数机制）

节点失效后如何实现节点的复制呢？

1. 读修复：读多个节点，发现旧版本就同步数据过去
2. 反熵：后台异步，发现不一致就处理



quorum法定人数机制：

w + r > n，一般w=r=(n+1)/2。key：读写节点集需要有一个重复的节点



quorum法定人数缺陷：

1. 写冲突，复制延迟等等等，quorum数据库一般是以最终一致来优化的
2. 旧数据监控的难题
3. 宽松quorum，虽然还是w与r，当新的节点可能不在之前的n中
4. 多数据中心



解决冲突：

1. 最后写入者胜利（丢失了持久性）。
2. 一个非常有意思的点：happen-before与并发。购物车例子。版本。
3. 多个主节点时，版本矢量。

# 数据分区



分区的主要目的就是负载均衡。

1. 关键字分区
2. 基于关键字的哈希值分区
3. 对于某些高频访问的热点数据——增加随机值



二级索引无法唯一的标识某一条记录，不能规整的映射到分区。一般二级索引的叶子是主键，而主键不一定是分区键，也就是没法通过二级索引直接确定数据的物理分区。innodb一般是每个分区分别建立独立的二级索引，没有全局的统一二级索引。



1.基于文档分区的二级索引：分区各自独立维护自己的二级索引

2.基于词条的二级索引分区：颜色作为二级索引，a到j放在分区1，k到z放在分区2.会造成写放大，一次更新可能涉及多个分区的数据。基本都不支持同步更新基于词条的二级索引更新。



分区再平衡（节点增减）：

1. 拒绝mod：变化太大
2. 固定数量的分区，10个节点，1000个分区，当增加节点时，统一从旧节点中取部分分区移到新节点，分区数量不变。只需要调整分区与节点的映射。
3. 动态分区：动态分裂&合并
4. 按照节点比例：前面的分区数量与节点数是分开的，这里的分区数量与节点数相关



手动与自动：毕竟分区不是天天都在变化。



读取数据的时候怎么知道取那个分区？

典型的服务发现问题。

1. 客户端随即选，没有就下一个，知道返回给客户端
2. 路由层
3. 客户端维护链接那个分区（其实就是分库了）

# 事务

事务的目的是简化应用层的编程模型。



## ACID

atomicity：出错时，可以终止事务，将部分完成的写入丢弃

consistency：逻辑概念，借助物理提供的AI达到C

isolation：并发的多个事务隔离

durability：持久化，严格意义上，并不会100%可靠，硬件也可能出错



许多分布式数据库，不支持多对象事务，因为涉及到分区。

涉及到多对象，手动开启事务并提交，部分nosql，没有多对象事务，将一起的多个文档更新，拆分为多个1个文档更新。

一条语句更新多个记录，关系型数据库一般没问题，但多部分nosql其实无法保证。

> “关系型数据库把‘一条 SQL 语句’视作一个不可分割的原子工作单元；而绝大多数 NoSQL（在未开启事务时）只把‘一个 Key/文档’视作原子工作单元。因此，一条更新百万行的 SQL 在 MySQL 中绝对原子，但在 MongoDB 中如果不加事务，就只是‘百万次单行操作的松散集合’，断电必出脏数据。”

对失败事务的重试，也没有那么完美



## 弱隔离级别



### 读已提交

脏读：锁/维护新旧两个值，当前事务读新的，其余读旧的。

脏写：一把锁，保平安



### 快照级别隔离与可重复读

rc级别存在不可重复读：

快照级别的隔离，读的是快照。mvcc，维护一个当前事务开启后执行第一条语句时的系统正在运行的事务列表。小于min可见，大于max不可见，其余（min到max）在表内不可见，表外可见。



索引与快照：1.索引指向所有版本；2.写时复制，更改父节点指向。



### 并发写

rc与rr，均是为了解决只读事务在遇到并发写时，可以看见什么。并发写呢？

1. 原子写，set a=a+1 （有些orm 会将其修改为 read-modify-write）
2. for update，加锁
3. 自动检测更新丢失（pg rr & oracle的串行化，mysql rr不支持）
4. cas：update set new where old
5. cow 或者冲突解决

## 串行化

1. 严格串行执行（redis的单线程、存储过程封装事务）（事务短、内存中运行、吞吐量低、跨分区事务少）
2. 两阶段锁定（两阶段加锁，指的是数据库整体层面区分为加锁时间段，释放锁时间段。读需要读锁，写需要写锁。）（什么还有谓词锁？）
3. 乐观并发控制（可串行化的快照隔离SSI，读快照，写假设没冲突，提交时判断是否有冲突（基于过期条件、是否读了mvcc旧值等等））

关于事务部分的总结：

事务属于一个抽象层，用于简化应用层的编程模型。隔离级别从，读已提交到可重复读，再到串行化，分别为了解决：

1. 脏读
2. 脏写
3. 读倾斜（不可重复读）
4. 更新丢失：read-modify-write  需要for update 
5. 写倾斜：写时，之前的判断已不成立，只能串行化
6. 幻读：间隙锁，实体化冲突

串行化：

1. 单线程/存储过程
2. 2PL
3. 可串行化快照隔离

# 分布式系统的麻烦



单节点，我们默认要么成功，要么失败，总之没有中间状态。宁可崩溃，也不要一个错误的数据。多节点时：存在部分失效。

## 网络的不可靠

物理故障或拥塞等等，我们在现实中很难获得一个明确的时间（传输+处理），用以判断一旦超过这个时间消息就是出问题了。

超时时间不应该是一个不变的常量，应该持续的观测，动态调整。



## 时钟的不可靠

分布式涉及到多台机器，而每台机器有自己的时钟，严格意义上没有精准的全局时钟。将顺序严格依赖于时间可能没那么可靠，逻辑的先后顺序比时间的先后顺序更可靠。



日历时间：涉及到同步，可能发生回溯或跳跃。

单调时间：自启动后的单调递增的时间，内部的良药，但却是分布式的毒药（每台机器都有各自的单调时间）。

逻辑时钟：与其费力同步几点几分，不如系统之间传递一个递增的数字。





依赖日历时间，可能发生与事件逻辑顺序不一致的情况。单调时间，则完全不能在分布式中使用，因为基本的共识都没有。

> * **跨节点传递超时（Timeout）时，传“截止时刻（Deadline）”而非“时长（Duration）”**：  
>   比如发起RPC调用时，客户端会计算当前**日历时钟** `+ 超时时间`，得到一个绝对时间戳（如 `2026-07-15 18:00:00.000`）传过去。服务端收到后，不断用本地的**单调时钟**检查“当前是否超过了这个截止时刻对应的单调读数”。这样即便服务端的日历时钟发生回拨，也不会影响超时判断。
>
> * **分布式锁（如 Redis Redlock 或 Zookeeper）绝对不靠时间戳判断**：  
>   它们依赖**版本号（zxid）**或**自增序列号**。如果一个锁的持有者因为Full GC暂停，醒来后发现自己本地时钟变慢了，它不会主动续期，而是依赖共识算法（Raft/Paxos）的法定人数投票来决定谁拥有最新数据。





进程暂停：

```java
while (true) {
    request = getIncomingRequest();

    // 确保租约始终至少有 10 秒的剩余时间
    if (lease.expiryTimeMillis - System.currentTimeMillis() < 10000) {
        lease = lease.renew();
    }

    if (lease.isValid()) {
        process(request);
    }
}
```

在前面时间校验通过后，process行，进程切换暂停超过10s，开始处理时，其实租约已经不属于本台机器了。

除了进程的切换，GC也可能导致系统临时不可用。将系统的GC视为计划内的临时理想，当作系统下线来处理。



## 知识、真相、谎言

分布式系统，很少使用共享内存，基本通过网络来与其他节点交流。只能通过收到（或者没收到）信息来进行抉择。但是网络又是不可靠的，没法区分是网络的问题还是节点的问题。——当观察与感知变得不可靠的时候，如何来获取有效知识并用于判断？



### 多数仲裁

节点没办法依据自身的信息判断节点状态：

1. 节点收到信息并处理，但所有的返回都被网络丢失了。虽然自己正常，但被其他节点判断为失效
2. 节点能意识到其返回被丢失了，但无法避免被其他节点丢弃
3. 节点单纯的GC了一分钟，自己认为自上次正常通信后什么问题都没有，但在其他节点已宣布其失效了



只能依赖法定票数，多数人仲裁。



### 主节点与锁

系统需要唯一的主节点，但某个节点可能自认为唯一，实际并没有获得法定票数。某节点曾经是主节点，但GC了一分钟，被其他节点判断为失效，并选举了新的主节点，此时该节点活过来了！



分布式锁和租约：租约的问题在于可能的暂停或延迟，导致实际写入数据库时，租约其实已经不被A持有了。一种方式时对共享资源的使用，带上fencing令牌，而租约重新被获取后，令牌原子递增，当共享资源发现旧令牌时拒绝执行。



> 对于单一原子操作，数据库自带的乐观锁（条件写入）即可取代分布式锁；但对于涉及多个资源（多服务/多副本）的复杂操作，必须引入“单调递增的隔离令牌”，以确保“租约过期”的旧客户端在任意资源上都无法造成破坏。

# 一致性与共识

事务提供了一个编程模型，这个模型中，利用数据库的能力实现将多个操作视为一个整体的原子性操作。复制或分区，讨论的是如何将多个分布式数据库节点视作完整的一个节点来对外提供服务。分布式则更广泛，除了数据库还有服务，如何将多个服务节点，管理起来，作为逻辑上的唯一节点对外提供服务？前面讲了分布式系统的挑战，网络的不可靠、时钟的不可靠，节点还会暂停或崩溃，需要依赖多数人选举，租约中使用fencing令牌。如何将底层分散的服务通过协议，整合成逻辑上的统一服务？单机上要么成功要么失败，如何处理作为集群的部分失败呢？事务的抽象是ACID，分布式系统的抽象则是：共识。共识达成了逻辑上作为一个整体的目标。



事务的隔离也有一致性，譬如要求提供同一个事务中的一致性。mvcc+间隙锁。

分布式中的一致性：针对延迟或故障，来协调副本之间的状态。



## 线性一致性



### 可线性化是什么？

最终一致性，只保证数据最终会收敛，但不保证何时。



**可线性化是什么？**

分布式中的可线性化指的是，对于分布式系统，外部调用者，就像只有一个副本一样。一旦写返回成功后，所有的读都一定是读的最新值。写请求在发起到返回成功之间（存在并发，无法确定读的具体值），只要有一个读到了最新值，后续所有读都必须是最新值。

可线性化（Linearizability）：分布式系统／并发对象的一致性模型，管的是**单个对象上的单个操作**——系统要表现得仿佛数据只有一份，每个操作都在"发起调用"与"收到响应"之间的某个瞬间原子地生效。



**与事务中的串行化区别是什么？**

事物中的串行化隔离级别要求所有涉及到相同资源的事务，串行化执行，确保事务执行的结果与串行执行一致。数据库同时支持 可串行化+线性化=严格可串行化（两阶段加锁及实际串行执行满足线性化，但可串行化快照隔离因为从快照读取数据，没有快照创建点之后的数据，不满足线性化）

可串行化（隔离级别，Serializability）：数据库事务的最高隔离级别，管的是**跨多个对象、包含多个操作的事务**——多个事务并发执行的结果，等价于按**某一种顺序**逐个串行执行。

1. 线性化只保证单次的原子性，不保证组合的原子性，值班医生的写倾斜例子，每个操作都是线性的，但组合起来就不满足串行化。
2. 实时序：近因性 vs 只要求"存在某个顺序"。线性化有时序性，可串行化，允许时间是后发生的事，表现的想先发生。只要求有顺序，但不要求顺序必须与时间一致。
3. 线性化是局部我只管这一个值的这一次操作，可串行化是整体，对这个值的多次操作，甚至跨值。



**与并发调度中的可串行化的区别又是什么？**

正确的并发调度顺序，等价于某个串行化的调度。

可串行化（调度判定）：并发控制理论中判定一个具体调度是否正确的形式化标准——给定一个操作交错序列，判断它是否等价于某个串行调度（冲突可串行化、视图可串行化）。





### 哪些依赖于可线性化？

1. 锁（锁的实现必须要满足线性一致性，一旦有节点获取到锁，所有节点都必须正确认识到锁已被获取）
2. 唯一性保证：系统需要确保名称唯一等等
3. 跨通道的时间依赖：一方面往mq发消息，另一方面往分布式存储中写数据，需要一致性保证，mq消费时读取的是最新的数据而不是旧数据。





### 如何实现线性化？

作为容错最重要的复制机制

主从：主节点或者同步复制节点读是线性的

主主：不可线性化

无主：可能不是线性化，即使严格的正确的法人选举（除非无故障，且时钟同步一致，否则松散的法人及最后写入胜利等会导致不满足线性一致），总之还是默认无主不满足线性一致。

分布式共识算法：是线性化的



### 线性化的代价？

性能损失

再看CAP：其实分区容错没得选，也不可控。我们只能在发生网络分区后，一致性与可用性之间做选择



## 顺序

顺序往往蕴含了因果。



### 因果一致性是什么？

线性一致是全序（传递+反对称+三分性（要么A关系B，要么B关系A，必须要满足且仅满足其中一个）），有一个统一的排序。

因果一致是偏序（Partial Order），有因果关系，则有顺序，没有因果关系的并发执行，无法排序。（偏序：传递性+反对称性）

> 反对称性：**如果 `A ≤ B` 且 `B ≤ A`，那么必然有 `A = B`（A和B是同一个元素）。**
>
> ≤ 为关系，对称性则是A≤B，必然有B≤A





### 如何实现因果一致性？

如何捕获因果关系？必须要知道谁前谁后。

1. 全局序列号
2. lamport 兰伯特时间戳（1.节点，2.每个节点有自己的计数器，3.当一个节点收到最大计数器值大于自身计数器值的请求或响应时，它立即将自己的计数器设置为这个最大值。）

![img](https://ddia.vonng.com/v1/ddia_0908.png)

1&2 其实都实现了全序。



对于如何在分布式系统中实现名称唯一性的问题，仅仅依靠序列得到全序还不满足，因为单个节点收到请求的时候，不知道其他节点的请求及对应的序号，无法决断当前请求应该成功还是失败。需要：全序广播（原子广播）。是分布式系统的绝对排序器。



全序广播：可靠交付（不丢消息）+全序一致（所有节点收到的消息一致）

全序广播是异步的，不保证线性一致。加上实时性就能保证线性一致了。

全序广播，可以用来实现状态机复制（相同顺序执行操作）

### 支持容错的共识

共识算法必须满足以下性质：

- 一致同意（Uniform agreement）

  没有两个节点的决定不同。

- 完整性（Integrity）

  没有节点决定两次。

- 有效性（Validity）

  如果一个节点决定了值 `v` ，则 `v` 由某个节点所提议。

- 终止（Termination）

  由所有未崩溃的节点来最终决定值。



全序广播相当于重复进行多轮共识（每次共识决定与一次消息传递相对应）

主从复制中，如何防止脑裂？——主节点带上一个递增的编号。先确认是不是主节点，然后再发起共识投票。
